# 18 — Real Herdr plugin conformance harness

**Status: plan (not built).** This spec adds a harness that runs popular Herdr plugins, unchanged, against Vibeke's compatibility layer. It also compares what the plugins draw in Vibeke with what they draw in the pinned Herdr baseline. It implements part of [07](07-api-cli-plugins.md) §8.4 item 2 ("unmodified plugins") and [10](10-quality-performance-testing.md) §4.8.

The harness is a regression signal. It is not the M5 certification gate. A sample of popular plugins cannot prove full compatibility (07 §8.0). The full inventory and the differential suite remain required.

## 1. Goals

- Install the 20 most-starred Herdr plugins that support macOS or Linux. Use pinned commits and unchanged manifests and source.
- Run every action, event hook, pane placement, startup command and link handler that each plugin declares. Assert the specific effect of each step.
- Classify every result, so that a failure points at a compat gap, a broken dependency or a step that was not run.
- Compare the plugin's own pane contents in Herdr 0.9.3 and in Vibeke. Show both side by side for human review.
- Never run third-party plugin code on a developer machine or with repository secrets.

## 2. Non-goals

- Comparing whole screens. Herdr and Vibeke draw their own frames, sidebars and tab bars. Running Herdr's own TUI against Vibeke is out of scope (07 §8.0). Only the plugin's pane is compared.
- Pixel-exact comparison. Fonts and renderers differ; the harness compares terminal cells.
- Certifying compatibility, or widening the advertised baseline.
- Windows. It joins with M6.

## 3. Current state

| Piece | Where | State |
|---|---|---|
| 99 real manifests pinned by commit and sha256 | `tests/compat/herdr/0.9.3/manifests/` | Checked statically: sha256, ids, actions, events, qualified action resolution and platforms (`crates/vk-compat/tests/herdr_manifests.rs`). No plugin is run. |
| Plugin system tests | `crates/vibeke/tests/it/compat_herdr_plugins_ext.rs` | Synthetic plugins installed from `file://` Git mirrors. Has its own private `Session` and helpers. |
| Differential harness | `crates/vibeke/tests/it/compat_herdr_diff.rs` | CLI scenarios only. A normal `#[test]` that returns early unless `VIBEKE_HERDR_DIFF=1`. It runs `--version` before the optional sha256 check. Never run. |

| Callback audit | `crates/vk-server/src/compat.rs` (`plugin.api_call`) | Records plugin, invocation, method, success and error code for mutating calls only, without params. Tests enforce this boundary. |

The plugin catalog (`https://assets.herdr.dev/plugins/index.json`) lists `stars`, `headCommit` and `platforms` for each repository. The existing manifest index keeps rank and provenance but not star counts.

What the top 20 need, from their manifests: builds that download moving release binaries (`curl … | bash`), toolchains (cargo, go, bun, node/npm), overlay, split, tab and popup pane placements, `[[startup]]` commands, `link_handlers`, and events (`pane.agent_status_changed`, `pane.agent_detected`, `worktree.created/opened`, `tab.*`, `workspace.*`, `pane.created/focused`). Some declare no actions: one plugin has only event hooks and one has only panes.

## 4. Security and isolation (first milestone, before any plugin build runs)

Legacy plugin trust is arbitrary code execution on the host. The harness therefore:

- runs plugins only on ephemeral CI runners (`ubuntu-latest`, `macos-14`) or a disposable VM. The test refuses to run unless `VIBEKE_HERDR_PLUGINS=1` is set, and the workflow is the only documented caller;
- gives each plugin a fresh HOME, XDG dirs, TMPDIR and runtime dir, and an allowlisted environment. It does not rely on the scrubbing in `vk_compat::herdr::launch`, which inherits more than the harness needs. No host credentials, `SSH_AUTH_SOCK`, cloud keys or GitHub tokens;
- sets a timeout and resource limits for every step, and tears down every process group the plugin started;
- uses a workflow with `permissions: contents: read`, `persist-credentials: false` on checkout, and no secrets. Untrusted builds use their own cache namespace and never write to the Rust caches that `weekly.yml` and `nightly.yml` share;
- keeps issue-writing authority in a separate job. That job reads the uploaded report artifact and never runs plugin code;
- redacts traces and screen captures with `vk-redact` and bounds their size before upload. Nothing captured is committed without review.

## 5. Corpus lock

`tests/compat/herdr/0.9.3/plugins/top20.lock.toml`, generated by `scripts/herdr-plugins-lock.ts` (bun):

- Input: a checked-in catalog snapshot with its sha256 and `generatedAt`. CI never fetches the live catalog to choose plugins.
- Selection: sort by `stars`, keep plugins whose manifest platforms include `macos` or `linux`, drop entries on the maintainer exclusion list, take 20. The exclusion list identifies repositories by the catalog's numeric `id` with a neutral reason, so the lock does not name excluded projects.
- Per plugin: repository, numeric id, plugin id, manifest path (subdirectory), commit, manifest sha256, stars at snapshot.
- Reuse the pins in `manifests/index.json` where the commit matches. Moving a pin forward is a reviewed change to the lock.
- A weekly `--check` mode compares the live catalog and reports drift (new top-20 entrant, new head commit). It never edits the lock.

A second section, the **execution lock**, records per plugin and platform the toolchain versions (node, bun, go, rust) and the sha256 of every artifact the build downloads. A changed artifact fails as `dependency_failure` ("dependency changed"), not as a compat failure. `mise.toml` does not pin Node or Go today; the harness workflow pins them itself.

## 6. Installation path

The harness installs through the real Git source path:

- `scripts/herdr-plugins-fetch.ts` mirrors each repository at its pinned commit into `<mirror>/<owner>/<repo>` (cache: `VK_HERDR_PLUGIN_CACHE`, default `~/.cache/vibeke/herdr-plugins`).
- The test installs `owner/repo[/subdir]@<sha>` with `VIBEKE_TEST_HOOKS=1` and `VIBEKE_PLUGIN_GIT_BASE=file://<mirror>` (`crates/vk-compat/src/herdr/source.rs`; the same mechanism `compat_herdr_plugins_ext.rs` uses).
- After install it checks that the checkout is at the pinned commit and that the manifest sha256 matches the lock.
- Builds may use the network. Build outputs are cached by (repository, commit, OS, architecture, execution-lock hash).

## 7. Scenarios

Each plugin has a hand-written scenario at `tests/compat/herdr/0.9.3/plugins/scenarios/<owner>__<repo>.toml`. Running every manifest action blindly produces false failures: for example, a file picker action needs a handoff file, and an `open-link` action must arrive through a link handler.

A scenario lists:

- **setup**: repositories, worktrees, files and a fake agent (for `pane.agent_status_changed` and `pane.agent_detected`);
- **steps**, in order: an action invocation with its context, an event trigger, a link to open, a server restart, a lifecycle command;
- **expectations** per step (§7.1);
- **stubs** for external services and credentials only (chat bots, tunnels, cloud machines). Herdr callbacks and plugin code are never stubbed;
- **expected outcomes** with a reason, for steps that cannot pass yet.

### 7.1 Evidence that a step ran

Absence of errors is not success. Every step needs positive evidence:

- the invocation reaches a terminal log state (completed or failed), not only "launched";
- the expected pane appears at the declared placement, or the popup appears (a popup result has `pane: null` and needs its own check);
- the pane screen contains the expected text after it is stable;
- an expected state file or event-hook log line appears;
- a long-running startup command reports ready before dependent steps run.

### 7.2 Lifecycle steps

Install, trust, build, link and unlink, startup before dependent actions and exactly once per activation, no startup on enable, config and state kept across reinstall, disable rejects callbacks, revocation rejects callbacks, uninstall removes managed files and registration. Broker closure ends connections; uninstall does not kill a plugin's own services, and the scenario tears those down explicitly.

### 7.3 Outcomes

Each step and each plugin ends in one outcome:

| Outcome | Meaning |
|---|---|
| `passed` | All expectations held. |
| `compat_failure` | Vibeke behaved wrongly. Links an inventory row in `docs/herdr-compat-inventory.md`. |
| `dependency_failure` | The build or an external dependency failed or changed. |
| `not_exercised` | The step did not run, with a reason. Never silent. |

### 7.4 First plugins

Milestone 1 starts with five plugins that together cover the categories 07 §8.4 item 2 names:

- layout or worktree workflow: `cloudmanic/herdr-plus` or `eugenioenko/ttt`;
- event notification: `alexarthurs/herdr-sidebar`;
- link handler: `ChmaraX/herdr-nvim`;
- stateful startup restoration: `eliasstravik/herdr-projects`;
- raw socket callbacks: to be found by reading the corpus source. If none of the top 20 uses them, add the most-starred plugin that does.

## 8. Observation

Reuse first: `events.read`, invocation logs, the `plugin.api_call` audit and pane-open audits.

Add narrow, test-only tracing (`VIBEKE_HERDR_TRACE=<file>`) only for what those miss:

- launcher argv and CLI parse errors, which happen in `vk-cli` before broker dispatch;
- raw-socket method names and error codes at the broker, since raw clients bypass the launcher.

Each line records plugin id, invocation id, transport, method or argv, result kind and error code. Params are omitted unless a scenario asks for them, and then they are redacted. The trace marks hits on `partial` or `missing` inventory entries as warnings and fails on `method_not_found`, `unsupported` and CLI parse errors.

## 9. Visual comparison

### 9.1 Same geometry

Both sides use the same terminal size. The harness records the position and size of every plugin pane after each step. A split or overlay of a different size than Herdr's is a finding on its own, and the cell comparison for that step stops there.

### 9.2 Capture

- **Vibeke:** `pane.screenshot` with `format = "ansi"` for comparison and `format = "png"` for viewing.
- **Herdr:** run the pinned binary in a pseudo-terminal with no window. Feed its output into `vk-term`, crop the plugin pane's rectangle, and keep the cell grid. The rectangle comes from Herdr's API if the baseline schema reports pane geometry; otherwise from the layout the scenario produces. Which one applies is decided when the schema is captured (§10).
- Capture after the pane is stable: no change for a set interval, within a timeout. No fixed sleeps.

### 9.3 Compare

Compare cells: text, foreground and background color, and attributes (bold, italic, underline, inverse). Each scenario may declare masks for regions that change on their own (clocks, spinners, temp paths, ids). Masks are explicit rectangles or regexes, never "ignore the pane". A step passes when all unmasked cells match.

Plugins that draw live external data (browsers, dashboards, agent status) compare only geometry and fixed text, or mark the step `not_exercised` with a reason.

### 9.4 Report

Both grids go through the same PNG renderer, so fonts and colors cannot create false differences. For each plugin and step, the report shows Herdr, Vibeke and a diff overlay side by side. It is uploaded as a workflow artifact.

### 9.5 Before Herdr runs

Until milestone 4, Vibeke's captures can be checked in as reviewed golden snapshots (ANSI text, not PNG). A change in a plugin's rendering then shows up in review.

## 10. Differential mode against Herdr 0.9.3

- Build Herdr from source at `7b116c05bfda646af39d2524c54e70c751f57ee8`, or fetch the release asset. Record its sha256 in `baseline.toml`, and verify it **before** executing the binary. This also fixes the current order in `compat_herdr_diff.rs`. The operator's installed Herdr is never used.
- Capture `herdr api schema --json` and every CLI help page into the `pending` entries of `baseline.toml`.
- Run each scenario against Herdr in its own temp HOME, XDG dirs and runtime dir. Herdr needs its own observation: a recording proxy on its socket, since Vibeke's trace cannot see inside Herdr.
- Compare traces, logs, pane geometry, files in the plugin state dir and cell grids (§9).
- Use a stricter normalizer than the current one, which replaces every `*_id`, every numeric `*_ms` and every error message. Each scenario lists the fields to normalize explicitly. Stable plugin and action ids are compared exactly.

## 11. Runner and reports

- New integration test file `crates/vibeke/tests/it/compat_herdr_real_plugins.rs`, with a `mod` line in `tests/it/main.rs`. One `#[ignore]` test per locked plugin, run with `--run-ignored only` and `VIBEKE_HERDR_PLUGINS=1`. Without the variable, the tests fail with a clear message instead of running plugin code.
- Extend `tests/it/support/mod.rs::Session` (or add a plugin variant beside it) with HOME and environment control and the plugin helpers now private to `compat_herdr_plugins_ext.rs`. Move those helpers instead of copying them.
- Each test writes `target/herdr-plugins/<plugin>-<os>.json`. An aggregation step builds one Markdown and JSON matrix: plugin, stars, platform, outcome per step, surfaces used, gaps hit.
- Runtime results stay separate from the generated inventory, whose test checks exact equality (`vk_compat::herdr::inventory`). The inventory doc links to the latest matrix instead of carrying a runtime column.
- Workflow: a new `herdr-plugins.yml` with `schedule` (weekly) and `workflow_dispatch`, matrix over Linux and macOS, release-mode `vibeke`, plus the separate reporting job (§4).

## 12. PR-time coverage

There is no general trace replayer. Replay would need initial state, response-derived id bindings, plugin authority, event order and streams, and it would still only prove Vibeke matches itself.

Instead, interactions seen in real runs become small reviewed fixtures in `tests/compat/herdr/0.9.3/plugins/fixtures/`: initial state, the call, and the expected response shape. They run in normal CI against the compat endpoint through a real broker with the plugin's authority, so broker restrictions stay in the path. They guard regressions; they do not prove Herdr correctness.

## 14. Risks and open questions

- Build steps that download "latest" binaries are not reproducible from the repository commit. The execution lock detects change but cannot restore an old artifact. Option: keep a private artifact cache keyed by sha256.
- Some plugins depend on external services or agent CLIs. Stubbing them without editing plugin code may not be possible for every step; those steps end `not_exercised`.
- Twenty builds, some with cargo or go, may take 20–40 minutes cold. The build cache (§6) and per-plugin parallel jobs keep warm runs short.
- Herdr's API may not expose pane geometry. Then cropping depends on the scenario's layout and the Herdr TUI's frame size, which is more fragile.
- Popularity changes weekly. The lock and drift report keep the corpus stable between deliberate updates.
