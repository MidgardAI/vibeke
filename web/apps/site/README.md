# Vibeke product website

TanStack Start / Router, React, Tailwind CSS v4, and self-hosted Geist fonts. The public product site is separate from the paired-device PWA and Electron apps.

From `web/`:

```sh
bun install
bun run dev:site       # http://localhost:3000
bun run build:site     # prerenders the landing page, comparison, and every docs chapter
bun run preview:site   # preview the production build
```

## Documentation

Edit the canonical Markdown in `docs/site/src/`, not a second website copy. The Vite content plugin resolves mdBook includes, rewrites chapter links, and builds the search index and table of contents. Changes reload during development. The API page reads method parameters and results from `docs/api/methods.json`. It has search, group filters, and expandable details. The build also serves the catalog and JSON Schema at `/api-reference/`. The mdBook build remains available.

Add new chapters to both `content/manifest.ts` and `docs/site/src/SUMMARY.md`. CLI, configuration, and API chapters are generated by Rust's existing `api_docs` tests; do not edit those references manually. Update them using the command documented in the generated files.

`src/lib/comparisons.ts` contains the comparison and its official sources. `/compare` has one table for all products, with product and feature filters. Short labels keep the table compact. Select a feature to read details and sources. The landing page links to that table. Update the review date when checking sources again. Describe the same feature for every product. Keep remote access, workspace transfer, and process recovery distinct. Avoid unverified price or performance claims.

## Copy

Use [ASD-STE100 Issue 9](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf) for the copy review:

- Use direct, active sentences and consistent technical terms.
- Use at most 20 words for an instruction and 25 words for a description.
- Give one instruction per sentence. Put a condition before its instruction.
- Keep paragraphs to one topic and at most six sentences.
- Avoid contractions, semicolons, idioms, and vague claims.
- Use American English. Keep commands, API identifiers, paths, and UI labels exact.
- Use domain terms where necessary: agent, pane, workspace, worktree, host, holder, sandbox, gateway, relay, transcript, and preview.

Review vocabulary against the STE dictionary as well as these rules. Sentence counts alone do not establish full compliance. Product names and technical terms need their specific meanings. Reference signatures and configuration examples retain their source syntax. Change their prose in the generator or source specification, then regenerate the reference.

## Checks

```sh
bun run --cwd apps/site typecheck
bun run --cwd apps/site test
bun run build:site
bun run e2e:site
```

Browser tests use the built production preview on port 3100. On macOS they use installed Chrome. On Linux, install Chromium first with `bun run --cwd apps/site e2e:install`. Tests cover direct docs routes, includes, anchor targets, mobile overflow, copy, search, comparison filtering, the screenshot gallery, and 404 responses. Desktop/mobile screenshots are saved in `apps/site/test-results/`.

## Serving and deployment

Nitro builds the server and static pages. `bun run build` uses the local Node server preset. `bun run preview` serves the result, including HTTP 404 responses for missing pages.

The Vercel project is `your-team/vibeke-dev`. Its production domain is `vibeke.dev`. The `www.vibeke.dev` project domain redirects to the root domain with status 308.

Deploy from `web/apps/site/`:

```sh
vercel link --yes --project vibeke-dev --scope your-team
vercel pull --yes --environment production --scope your-team
VERCEL=1 bun run build
vercel deploy --prebuilt --prod --scope your-team
```

This uploads the compiled site, including the documentation. It does not require the Rust workspace on Vercel. Run the checks above before each deployment. To test the deployed site, run `PLAYWRIGHT_BASE_URL=https://vibeke-dev.vercel.app bun run e2e`. Regenerate the references first if API or CLI definitions changed.

The landing page uses captures of the TUI, Electron app, and web app with sample workspace data. Select an app to bring its screenshot forward, or open it at full size. The gallery does not connect to a live session.

To refresh the screenshots, build `target/debug/vibeke`, the desktop app, and the PWA. Install Chrome and tmux. From `web/apps/site`, run:

```sh
bunx tsx scripts/capture-clients.ts
```

The script starts an isolated session, gateway, and local relay. It creates sample repositories, conversations, and permission requests. It captures the actual Electron and web interfaces with Playwright. It captures the running TUI through tmux and renders its ANSI output with the original colors. `public/screenshots/capture.json` records the capture date and source commit. Temporary processes and data are removed when the script exits.

## Branding

The logo is the approved “Duck in a shell” concept. The shared source is
`design/brand/duck-in-a-shell.png`. Run `bun run icons` from `web/` to refresh
the website, PWA, and Electron exports. Keep the source and generated assets
with the generator changes. The site serves PNG and ICO favicons, an Apple
touch icon, a web manifest, and a 1200 × 630 link preview.
